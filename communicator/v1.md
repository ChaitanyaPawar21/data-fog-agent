# Data Fog Agent — Build Spec

An agentic AI system that **finds, explains, cleans and protects** a company's scattered data.

Read this whole file before writing code. Build in the phase order at the bottom. Do not start a phase until the previous phase's acceptance criteria pass.

---

## 1. Product summary

Companies have data spread across databases, file drives and chat. Nobody knows what exists, which copy is correct, who owns it, or where personal data sits. This system:

1. **Fog Eraser** — connects to sources, builds one catalogue of all data assets, and answers natural-language questions (including running safe read-only SQL).
2. **PII Guard** — finds personal data (Aadhaar, PAN, phone, email, names, addresses), tags it, and masks it in answers.
3. **Auto-Docs** — writes descriptions for undocumented tables, columns and files; owners approve them.
4. **Trust Score + Stale Alerts** — scores every asset and alerts when data goes stale.
5. **File Merger** — finds duplicate/overlapping files, proposes a merge, and executes it only after human approval.
6. **MCP Server** — exposes the catalogue and tools to Claude and other MCP clients with the same permissions.

Core principle: **the agent proposes, humans approve.** Nothing destructive happens without approval, and nothing is ever deleted (only archived).

## 3. Coding rules (follow strictly)

- Correctness first, simplicity second, maintainability third.
- Write code like a practical human developer. No AI slop.
- No unneeded classes, interfaces, factories, managers, wrappers, or abstraction layers. A plain function is the default.
- No helper functions for trivial operations. No defensive checks for impossible cases.
- Clear, specific names (`sync_postgres_source`, `mask_pii_values`), never generic ones (`process_data`, `handle_operation`).
- Short functions, one responsibility each, no deep nesting.
- Comments only where the reasoning isn't obvious. Never restate the code.
- No logging, retries or error handling layers beyond what the feature actually needs.
- Do not add dependencies outside the stack above without a clear reason.
- When editing existing code: read the surrounding code first, follow its conventions, make the smallest correct change. Don't rewrite unrelated code.
- Never trade away security or correctness to make code shorter.

## 4. Architecture

```
Next.js frontend ──► FastAPI (auth, REST API, MCP endpoint)
                          │
            ┌─────────────┼────────────────┐
            ▼             ▼                ▼
       Agent service   Catalog API    Proposals/Approvals API
            │             │                │
            └─────────────┴────────┬───────┘
                                   ▼
                    Postgres + pgvector (catalogue, PII tags,
                    permissions, proposals, audit log)
                                   ▲
                    arq workers (Redis queue, scheduled jobs)
                    ├── connectors: postgres, files, slack_export
                    ├── sync jobs (incremental)
                    ├── pii scan
                    ├── auto-docs generation
                    ├── trust score + stale check
                    └── merge candidate detection
```

Rules:
- Slow work (syncing, scanning, LLM doc generation, merging) runs **only** in workers, never inside API requests.
- The LLM never receives connector credentials and never receives unmasked PII.
- Every permission check happens in backend code, never left to the LLM.

## 6. Data model

All tables except `orgs` have `org_id`. Enable Postgres row-level security on every table using `org_id`.

```
orgs(id, name, created_at)
users(id, org_id, email, password_hash, name, role[admin|member], created_at)
groups(id, org_id, name)
user_groups(user_id, group_id)

sources(id, org_id, type[postgres|files|slack_export], name,
        encrypted_config, sync_cursor jsonb, last_synced_at, status, last_error)

assets(id, org_id, source_id, type[table|file|channel], name, path,
       description, description_status[none|proposed|approved],
       owner_user_id null, row_count null, size_bytes null,
       last_modified_at, last_seen_at, archived bool default false,
       trust_score int null, embedding vector(<dim>), content_hash)

columns(id, asset_id, name, data_type, description, description_status,
        pii_type null)

asset_permissions(asset_id, group_id)      -- no rows = admins only

knowledge_snippets(id, org_id, source_id, text, author, posted_at,
                   embedding vector(<dim>))  -- from Slack export

proposals(id, org_id, type[merge|doc], status[pending|approved|rejected|done|failed],
          payload jsonb, created_at, reviewed_by null, reviewed_at null)

alerts(id, org_id, asset_id, type[stale|schema_change|pii_found],
       message, created_at, resolved_at null)

audit_log(id, org_id, user_id null, actor[user|agent|mcp|worker],
          action, target, details jsonb, created_at)

sync_runs(id, source_id, started_at, finished_at, status, assets_seen, error)
```

Encrypt `sources.encrypted_config` with Fernet using a key from env (`CONFIG_ENCRYPTION_KEY`).

## 7. Feature specs

### 7.1 Connectors (Fog Eraser foundation)

Each connector is a module with plain functions:

- `list_assets(config, cursor) -> (assets, new_cursor)` returns only assets changed since `cursor`.
- `sample_values(config, asset, limit=50)` returns sample values per column/field, used **only** for PII scanning and doc generation, never stored raw.

**postgres** — reads `information_schema` across allowed schemas. Asset = table/view. Captures columns, types, row count estimate (`pg_class.reltuples`), and last modified time where available (use `pg_stat_user_tables` last activity). Connects with a user that has read-only grants.

**files** — scans a folder (stand-in for Google Drive). Supports `.csv`, `.xlsx`, `.pdf`, `.txt`. For tabular files, store headers as columns. Use `content_hash` + modified time as the cursor. Folder sub-paths map to groups for permissions (configured per source).

**slack_export** — reads a standard Slack export folder (channels/*.json). Each channel is an asset. Messages become `knowledge_snippets` with embeddings.

Sync job (`sync_source`): run connector → upsert assets/columns → mark assets not seen in a full scan as `archived` → write `sync_runs` row → enqueue `pii_scan`, `generate_embeddings` for changed assets. Schedule: every 6 hours, plus manual trigger from UI.

Embeddings: embed `name + path + description + column names` for each asset.

### 7.2 Agent + chat (Fog Eraser)

`agent.py` runs a tool-calling loop (max 8 steps). Tools:

| Tool | Behaviour |
|---|---|
| `search_catalog(query)` | pgvector similarity + name match, filtered to `visible_asset_ids(user)`. Returns top 10 with trust score and owner. |
| `get_schema(asset_id)` | Columns, types, descriptions, PII tags. Permission-checked. |
| `run_sql(asset_source_id, sql)` | See SQL safety below. Returns max 200 rows with PII columns masked. |
| `search_knowledge(query)` | Searches Slack snippets the user can see. |
| `find_owner(asset_id)` | Owner name/email. |

System prompt rules: always cite which assets an answer came from; prefer the asset with the highest trust score when duplicates exist and say so; never guess numbers without querying.

Chat API streams the answer plus a `sources` list and optional `table` / `chart` data. Store conversations per user.

**SQL safety (`sql_guard.py`) — mandatory:**
1. Parse with `sqlglot`. Reject anything that isn't a single `SELECT` (no `INSERT/UPDATE/DELETE/DDL`, no multiple statements, no `COPY`, no functions like `pg_read_file`).
2. Reject queries touching tables the user can't see.
3. Execute with the read-only DB user, inside a transaction set `READ ONLY`, with `statement_timeout = 10s`.
4. Wrap with `LIMIT 200` if no smaller limit exists.
5. Mask columns tagged with PII in results before they reach the LLM or the user (unless user is admin and explicitly requests unmasked in UI — never via LLM).
6. Log every executed query in `audit_log`.

### 7.3 PII Guard

`pii_scan(asset_id)` job:
- Sample up to 200 values per column (or rows/cells for files).
- Regex rules: Aadhaar (12 digits, optional spaces, Verhoeff checksum), PAN (`[A-Z]{5}[0-9]{4}[A-Z]`), Indian mobile (`(\+91[\-\s]?)?[6-9]\d{9}`), email.
- Presidio for `PERSON` and `LOCATION`, used on text columns only.
- A column is tagged if ≥ 20% of non-null samples match. Free-text columns (`notes`, `comments`, logs) count if any sample matches.
- Store tag in `columns.pii_type`. Never store matched values.
- New PII found → create `pii_found` alert.

Masking: `mask_pii_values(rows, pii_columns)` replaces values with `XXXX` plus last 2–4 characters.

### 7.4 Auto-Docs

`generate_docs(asset_id)` job, run for assets with `description_status = none`:
- Give the LLM: asset name, path, column names/types, PII-masked sample values (max 5 per column), related Slack snippets.
- Ask for a one-paragraph asset description and one-line column descriptions in JSON.
- Save as a `proposals` row of type `doc`. The owner (or an admin) approves → copy into `assets.description` / `columns.description`, set status `approved`.
- Never overwrite an approved description automatically.

### 7.5 Trust Score + Stale Alerts

`compute_trust(asset_id) -> int 0..100`:

| Factor | Points |
|---|---|
| Freshness: modified in last 7 days 30, 30 days 20, 90 days 10, else 0 | 30 |
| Has owner | 20 |
| Approved description | 20 |
| Queried/searched in last 30 days (from audit_log) | 15 |
| Not part of a duplicate group | 15 |

Stale rule: asset not modified in 90 days but still queried in the last 30 days → `stale` alert. Schema change (columns added/removed/type changed during sync) → `schema_change` alert.

Daily cron job recomputes scores and alerts.

### 7.6 File Merger

`find_merge_candidates()` daily job, for tabular files only:
1. Group files whose normalised column sets match exactly (lowercase, trimmed). Also require name similarity ≥ 0.6 (difflib) **or** ≥ 30% overlapping rows.
2. For each group, pick a key column: a column that is unique in every file and named like `*_id`. If none, use full-row equality.
3. Compute: total rows, exact duplicate rows, conflicting rows (same key, different values).
4. Conflict rule: value from the most recently modified file wins. List every conflict in the proposal.
5. Create a `merge` proposal with payload: source asset ids, key column, row counts, conflicts (first 50), suggested output name.

On approval (`execute_merge(proposal_id)` job):
- Build merged file, write it to the source folder as `<name>_merged_<date>.<ext>`.
- Permissions of the new asset = **intersection** of source assets' groups (most restrictive).
- Run `pii_scan` on the result.
- Move originals into an `_archive/` subfolder and mark them `archived`. Never delete.
- Store everything needed to undo in the proposal payload. Provide an `undo_merge` action that restores originals and archives the merged file.
- Write `audit_log` entries for every step.

Out of scope for v1: files with different columns, database table merges.

### 7.7 MCP Server

`mcp_server.py` using FastMCP, mounted in FastAPI at `/mcp` (Streamable HTTP).
- Tools: `search_catalog`, `get_schema`, `run_sql`, `find_owner`, `list_pii_columns`, `propose_merge` (creates a pending proposal only).
- Every tool call resolves the calling user from the auth token and goes through the **same** functions and permission checks as the agent. No separate code paths.
- v1 auth: per-user API tokens created in the UI (hashed in DB). v2: OAuth.
- Log every call to `audit_log` with `actor = mcp`.

### 7.8 Auth and permissions

- Email + password, argon2 hashing, short-lived JWT access token + refresh token in httpOnly cookie.
- Roles: `admin` (manage sources, see all assets, approve anything) and `member`.
- `visible_asset_ids(user)`: admins see all; members see assets whose `asset_permissions` include one of their groups.
- Asset owners can approve proposals for their own assets.
- Rate-limit chat and MCP endpoints per user (e.g. 30 requests/minute).

- `support_db`: `tickets` with a free-text `notes` column containing some phone numbers and Aadhaar numbers, `app_logs` containing emails.
- Plant: amounts in rupees in `orders` and in paise in `orders_v2`; dates as text in `customers_backup_2023`; gross revenue in sales vs net in finance.

**Slack export** (`demo/output/slack/`): channels `#data`, `#sales`, `#finance` with messages like "use orders_v2 not orders", "Priya owns customer data", "finance revenue is net of returns", "amounts in orders_v2 are in paise".

Users and groups: admin, `sales`, `finance`, `hr`, `support` groups with 1–2 users each.

`ground_truth.yaml` lists: every duplicate group, every PII column (including hidden ones), stale assets, the correct merge result row counts, and correct answers to eval questions.

## 10. Evals (`evals/`)

`questions.yaml`: ~50 questions with expected answers or expected assets, e.g.:
- "Where is the latest orders data?" → expects `orders_v2`.
- "What was total net revenue in March 2026?" → expected number.
- "Which tables contain phone numbers?" → expected list including `tickets.notes`.
- "Who owns customer data?" → Priya.
- Permission checks: a `sales` user asking about `hr/employee_list.xlsx` must get no data.
- Safety checks: prompts trying to make the agent run `DELETE` or reveal unmasked Aadhaar must fail safely.

`run_evals.py` runs each question through the agent as the specified user and reports pass/fail. CI fails if the pass rate drops below the threshold set in the file. Also evaluate PII recall and merge candidate detection against `ground_truth.yaml`.

## 13. Non-negotiables

- Never execute non-SELECT SQL against connected sources.
- Never send unmasked PII or credentials to the LLM.
- Never delete user files or tables. Archive only.
- Every merge and doc change goes through an approved proposal.
- Every permission check is in backend code and shared by UI, agent and MCP.
- Every agent action, query, MCP call and approval is written to `audit_log`.
